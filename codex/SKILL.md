# Review Harness — 구축된 작업 환경 진단·최적화 (Codex CLI)

> **Codex CLI 전용 변형판이다** — 절차가 Codex의 구성 요소(AGENTS.md·
> `~/.codex/config.toml`·skills·rules·approval policy·sandbox)를 전제한다.
> Claude Code 사용자는 [../SKILL.md](../SKILL.md)를 사용할 것.

> design-harness가 **Gap을 채운다면**, 이 스킬은 **Gap이 사라졌거나 애초에
> 없었던 항목을 걷어낸다.** 같은 차집합을 반대 방향으로 돈다:
>
> ```
> 기존 harness − 모델이 이미 함 − 런타임이 이미 함 − 다른 층이 이미 맡음
>              − 실측 근거 있는 항목  =  제거 대상
> ```

> 하네스는 만들 때가 아니라 **모델이 좋아질 때** 낡는다. 작년에 정당했던 규칙이
> 올해는 모델 능력과 중복이 된다 — 리뷰는 1회성 청소가 아니라 모델 교체 주기에
> 맞춘 정기 작업이다.

## Codex 고유 전제 — 강제층의 형태

Claude Code는 훅(PreToolUse 등)으로 강제하지만, **Codex의 강제층은
`approval_policy` · `sandbox_mode` · `rules` 파일 · `[projects] trust_level`**이다.
이 차이가 D2(런타임 중복) 판정 기준을 바꾼다:

- `sandbox_mode`가 이미 워크스페이스 밖 쓰기를 막는데 "프로젝트 밖 파일을 건드리지
  마라"를 AGENTS.md에 적어 두었다면 **D2 중복**이다.
- `approval_policy`가 이미 명령 실행 승인을 받는데 "위험한 명령은 먼저 물어봐라"를
  지침으로 적어 두었다면 **D2 중복**이다.
- 반대로 비가역 Invariant가 AGENTS.md에만 있고 approval/sandbox/rules로 내려오지
  않았다면 **과소 하네스**이며 PROMOTE 대상이다.

## 원칙 (하드 레일)

1. **입증 책임 역전** — design-harness는 "만들 근거"를 요구했다. 리뷰는 반대다:
   **모든 기존 항목이 존치 근거를 스스로 대야 한다.** 근거를 못 대는 항목의
   기본 판정은 REMOVE이며, "이미 있으니까"는 존치 근거가 아니다. 단 모든
   REMOVE는 원칙 2와 §4 게이트를 통과해야 한다.

2. **능력 중복 ≠ 보장 중복** — 모델이 잘하는 일이라도 **한 번의 실패가 비가역·
   치명인 Invariant**의 강제층(approval·sandbox·rules)은 유지한다. 판정 질문은
   "모델이 이걸 하는가"가 아니라 **"모델이 이걸 안 한 경우가 한 번 있을 때
   복구 가능한가"**다. 복구 불가면 KEEP(강제층), 복구 가능이면 REMOVE. 같은
   Invariant가 AGENTS.md에도 있으면 **강제층이 이미 보장하므로 지침 쪽을 제거**한다.

3. **판정 근거 2단** — 모델 능력 판정은 [../references/model-baseline.md](../references/model-baseline.md)
   1차 선별 → 애매한 항목만 실측 ablation 2차(§3-b). 다음은 baseline만으로
   REMOVE 할 수 없고 ablation이 필수다: (a) baseline이 Tier B로 분류한 항목,
   (b) 사용자·프로젝트 고유 맥락이 걸린 항목, (c) 강제층 항목.
   baseline에 없는 능력을 "당연히 잘하겠지"로 채우지 않는다 — 없으면 Tier B다.

4. **판정에 모델 버전 각인** — 모든 능력 중복 판정에 `[verified: <모델>-<버전> /
   <YYYY-MM>]`을 남긴다. `model_reasoning_effort` 같은 설정도 능력에 영향을
   주므로 함께 기록한다. 모델 교체, 특히 **더 작은 모델·낮은 effort로의
   다운그레이드**는 이 표식 항목 전체를 자동 재검토 대상으로 만든다.

5. **측정 없는 최적화 금지** — "과최적화"는 체감이 아니라 수치로 판정한다:
   상시 로드 비용, 항목 수, 중복률, 미사용 기간. before/after 수치를 못 내는
   제안은 제안이 아니다.

6. **애매하면 KEEP + 관측 대기** — 근거를 **못 대는** 항목은 REMOVE지만, 근거가
   **갈리는** 항목(ablation 부분 통과, 사용자 판단이 엇갈림)은 WATCH 목록에
   올려 다음 리뷰까지 추적한다. 잘못된 제거가 잘못된 존치보다 비싸다.

7. **되돌릴 수 있게 제거** — 적용 전 백업 또는 커밋. `~/.codex/`는 git 관리 밖일
   가능성이 높으므로 타임스탬프 백업을 먼저 만든다. **`config.toml`은 한 줄
   오타로 세션이 안 뜰 수 있으니 수정 후 파싱을 확인**한다.

8. **제거 후 회귀 검증** — 제거는 끝이 아니라 **가설**이다. "이 항목 없이도
   동일하게 동작한다"를 대표 태스크로 확인하고, 실패하면 되돌린 뒤 그것을
   **관측 근거로 기록**해 다음 리뷰에서 다시 후보로 오르지 않게 한다.

9. **승인 후 적용** — 진단 리포트 → 사용자 승인 → 적용. 수정·삭제는 diff를
   먼저 보여준다. 파일 전체를 지울 때는 파일별로 따로 승인받는다.

## 진단 렌즈 — 중복(D)과 잔재(S)

### D — 중복 (다른 무언가가 이미 그 일을 한다)

| 코드 | 정의 | 판정법 | 기본 조치 |
|---|---|---|---|
| **D1 모델 중복** | 현재 모델이 지시 없이도 하는 것 | model-baseline Tier A 대조 → 애매하면 ablation | REMOVE |
| **D2 런타임 중복** | approval policy·sandbox·rules가 이미 막는 것의 재서술 | 실제 설정값으로 확인 (추정 금지) | REMOVE |
| **D3 층간 중복** | 같은 역할이 지침·도구·강제·검증층 중 둘 이상에 존재 | 역할 한 문장 대조 | MERGE (강제층 남김) |
| **D4 자산 중복** | AGENTS.md ↔ 스킬 ↔ 프롬프트 ↔ 플러그인 간 같은 규칙, 역할이 겹치는 파일 둘 | 트리거·대상·역할로 클러스터링 | MERGE |
| **D5 문서 중복** | README·공식 문서·다른 파일 내용의 복제 | 원본 위치 확인 | REMOVE (참조로 대체) |

D1의 대표 예 — 이런 규칙이 있으면 즉시 후보:
"코드 짜기 전에 계획을 세워라", "수정 후 테스트를 실행해 확인하라", "기존 코드
스타일에 맞춰라", "에러가 나면 원인을 추적하라", "관련 파일을 먼저 읽어라".

D2의 대표 예: sandbox가 막는 범위를 지침으로 재서술, approval 프롬프트가 이미
잡는 것을 규칙으로 재서술, `[projects] trust_level`로 이미 정한 신뢰 범위를
프롬프트에서 다시 설명.

### S — 잔재 (그 일 자체가 더는 필요 없다)

| 코드 | 정의 | 판정법 | 기본 조치 |
|---|---|---|---|
| **S1 Dead** | 참조 대상(파일·명령·경로·MCP 서버)이 존재하지 않음 | 실제 존재 확인 | REMOVE |
| **S2 Drift** | 지금 안 쓰는 도구·언어·워크플로우를 위한 항목 | 현재 자산과 대조 | REMOVE |
| **S3 Unused** | 스킬·프롬프트·rules가 N주간 호출 0회 | `~/.codex/history.jsonl`·세션 기록 grep, 불가면 "미확인" | WATCH → REMOVE |
| **S4 Speculative** | 근거가 "일반적으로 좋다"·미래 대비 | 근거 확인 | REMOVE |
| **S5 Over-specified** | 모델이 상황을 보고 더 잘 판단할 것을 못 박아 성능을 깎음 | ablation으로 유/무 비교 | REMOVE 또는 완화 |

### 조치 코드

`REMOVE` · `MERGE` · `MOVE`(더 가벼운 층으로) · `PROMOTE`(지침 → approval/sandbox/
rules 승격) · `KEEP` · `WATCH`

**PROMOTE를 빠뜨리지 말 것** — 비가역 Invariant가 AGENTS.md에만 있으면 그건 과소
하네스이며, 제거 목록과 같은 비중으로 보고한다.

## 절차

### 1. 하네스 인벤토리 — 파일이 아니라 **항목** 단위로

글로벌 하네스를 **실제로 읽고** 분해한다. 단위는 파일이 아니라 **규칙 한 줄 =
항목 하나**다.

스캔 대상 (존재하는 것만):

- `~/.codex/AGENTS.md` — 전역 지침 (**상시 로드**)
- `~/.codex/config.toml` — `approval_policy`·`sandbox_mode`·`model`·
  `model_reasoning_effort`·`[projects] trust_level`·`[plugins]`·`[marketplaces]`·
  MCP 서버 등록
- `~/.codex/rules/*.rules` — 강제층 규칙
- `~/.codex/skills/*/SKILL.md` (또는 `~/.agents/skills/`) — frontmatter의
  `description`은 **상시 로드**, 본문은 호출 시 로드
- `~/.codex/prompts/*.md` — 커스텀 프롬프트·슬래시 커맨드
- `~/.codex/plugins/` — 설치 플러그인이 주입하는 스킬·프롬프트
- 메모리 저장소(`memories_*.sqlite` 등) — 지침처럼 작동하는 상시 항목

각 항목을 원장에 적는다:

| ID | 위치 (file:line) | 층 | 역할 (한 문장) | 로드 | 원 근거(추정) |
|---|---|---|---|---|---|

역할을 한 문장으로 못 쓰는 항목은 그 자체로 후보다.

### 2. 상시 비용 측정

- **상시 로드**: AGENTS.md 전문 + 모든 스킬 frontmatter + rules + 활성 플러그인
  등록 정보 + 상시 메모리
- **조건부 로드**: 스킬 본문·프롬프트 본문

**이 둘을 섞어 세지 말 것.** "스킬이 N개나 된다"는 그 자체로 비용이 아니다 —
실제 상시 비용은 description N개의 합이다.

```
상시 로드   : <bytes> (≈<tokens> 추정)  — AGENTS.md <b> + 스킬 desc <b> + rules <b>
조건부 로드 : <bytes> / <파일 수>
총 항목 수  : <n>   (지침 <n> / 도구 <n> / 강제 <n> / 검증 <n>)
중복률      : <중복 판정 항목> / <전체> = <%>
미사용률    : <N주 호출 0회 자산> / <전체 자산> = <%>
```

토큰은 추정임을 명시한다(한글 혼용은 대략 바이트/2.5~3).

### 3. 판정 — 2단 하이브리드

#### 3-a. baseline 1차 선별

[../references/model-baseline.md](../references/model-baseline.md)와 대조한다.

- **Tier A** → D1 중복, REMOVE 후보
- **Tier C** → KEEP. 하네스가 존재해야 하는 영역
- **Tier B** 또는 **표에 없음** → 3-b로

#### 3-b. ablation 2차 (실측)

1. 그 항목이 다루는 **대표 태스크**를 정한다.
2. 그 항목을 **제거한 상태**를 재현한다 (임시 프로필·별도 워크스페이스·해당
   지침을 뺀 세션).
3. **K회 실행**하고 관측한다. K는 기본 3, 위험도가 높으면 늘린다.
4. 판정:
   - **K/K 통과** → REMOVE `[verified: <모델>-<버전> / effort=<값> / <YYYY-MM>]`
   - **0/K 통과** → KEEP, 관측 근거로 기록
   - **부분 통과** → 원칙 2 적용. 비가역·치명이면 KEEP 또는 PROMOTE, 아니면 WATCH

ablation을 실행할 수 없는 항목은 **"미판정"**으로 남긴다 — 추정으로 REMOVE 하지
않는다.

#### 3-c. 중복·잔재 교차 검사

D3·D4는 **항목 간** 검사다:

- 역할 한 문장이 같거나 포함 관계인 항목을 클러스터로 묶는다.
- **트리거가 같은 것**, **대상이 같은 것**, **금지 대상이 같은 것**을 각각 묶는다.
- 클러스터 안에서 가장 강한 층 하나만 남기고 나머지는 MERGE.
- 스킬끼리의 **트리거 충돌**(description이 겹쳐 어느 것도 확실히 안 뜸)도 D4다.

S1은 실제 존재 확인으로, S3는 `~/.codex/history.jsonl`·세션 기록에서 호출 흔적을
찾아 판정한다. 확인할 수 없으면 "미확인"이며, 미확인을 미사용으로 취급하지 않는다.

### 4. Invariant 보호 게이트

REMOVE·MERGE 후보 **전체**를 사용자의 Invariant와 대조한다:

- 이 목록 중 하나라도 안 지켜졌을 때 **복구 불가능**한 것이 있는가?
- 지금은 AGENTS.md에만 있는데 approval·sandbox·rules로 **강제되어야 하는** 것이
  있는가? (→ PROMOTE)
- 최근에 실제로 겪은 사고와 관련된 항목이 있는가? (→ KEEP, 관측 근거)

**이 게이트를 통과하지 않은 REMOVE는 적용하지 않는다.**

### 5. 최적화안 제시

| ID | 위치 | 역할 | 렌즈 | 근거 | 조치 | 검증 |
|---|---|---|---|---|---|---|

함께 보고한다:

- **before / after 수치** — §2의 모든 지표. 특히 상시 로드 감소분
- **조치별 그룹** — REMOVE / MERGE / MOVE / **PROMOTE** / KEEP / WATCH / 미판정
- **WATCH 목록** — 왜 미뤘는지와 추적할 신호
- **미판정 목록** — ablation을 못 돌린 항목과 이유
- **체급 재산정** — design-harness의 S/M/L 기준

**0개 제거로 끝나는 리뷰**는 하네스가 건강하다는 뜻이지 리뷰 실패가 아니다.

### 6. 적용 → 회귀 검증 → 다음 회차 예약

1. **백업/커밋**. `config.toml` 수정 후에는 **파싱 확인**(세션이 정상 기동하는지).
2. **적용** — diff를 보여주고 파일별로.
3. **회귀 검증** — 제거한 항목이 다루던 대표 태스크를 실제로 돌린다. 실패하면
   그 항목만 롤백하고 실패 관측을 KEEP 근거로 남긴다.
4. **다음 회차 조건**:
   - **재검토 트리거**: 모델 또는 `model_reasoning_effort` 변경 시 `[verified:]`
     표식 항목 전체. 다운그레이드는 무조건 전수 재검토.
   - **Kill Criteria**: 무엇이 보이면 이번 최적화를 되돌리는가.
   - **WATCH 만료**: 언제까지 신호가 없으면 REMOVE로 전환하는가.

## 과최적화 신호

- 상시 로드 지침이 **프로젝트 실제 코드보다 빨리 자란다**.
- 지침층 항목 수 > 사용자가 실제로 말할 수 있는 Invariant 수.
- 스킬 description이 서로 트리거를 다투어 **어느 것도 확실히 안 뜬다**.
- 한 목적이 여러 프롬프트·스킬로 쪼개져 있다.
- 모델·effort가 바뀌었는데 `[verified:]` 표식 항목이 그대로다.
- **규칙이 규칙을 참조**한다 (메타 규칙 층이 생겼다).
- 최근 N주 세션에 한 번도 등장하지 않은 스킬·프롬프트.
- "이전에 한 번 실수했으니까" 항목이 **원인 수정 없이** 누적된다.
- 같은 금지를 sandbox·rules·AGENTS.md에 삼중으로 걸어 두었다.
- 모델 일반론("LLM은 ~를 못한다")이 근거로 적힌 항목.

## 과소 하네스 신호 (같이 본다)

- 비가역·치명 Invariant가 AGENTS.md에만 있다 (→ PROMOTE).
- `approval_policy`·`sandbox_mode`가 프로젝트 위험도에 비해 느슨한데 지침으로만
  보완하고 있다.
- 완료 판정이 모델의 자기보고("됐습니다")에 의존한다 (→ 검증층 부재).
- 같은 실패를 반복 관측했는데 대응 항목이 없다.
- Tier C 영역인데 아무 항목도 없다.

## 산출물이 아닌 것

- **무조건 줄이는 도구가 아니다** — 0개 제거도 정상 결과이며, PROMOTE로 오히려
  강화되기도 한다.
- **모델 벤치마크가 아니다** — baseline과 ablation은 하네스 항목 판정용 최소
  근거이지 능력 평가가 아니다.
- **설계 스킬이 아니다** — 빈 Gap이 발견되면 design-harness로 넘긴다.
- **도메인 지식을 대신 공급하지 않는다** — 무엇이 비가역·치명인지는 사용자
  답변에서 온다. 답이 없으면 미판정으로 남긴다.
