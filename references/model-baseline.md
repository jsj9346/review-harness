# Model Capability Baseline

> **버전 스탬프: 2026-08 / 대상 세대 — Claude 5 계열(Fable 5·Opus 5·Sonnet 5),**
> **Haiku 4.5, GPT-5 계열**
>
> **신선도 규칙**: 이 표는 6개월 또는 모델 세대 교체 중 먼저 오는 시점에
> 만료된다. 만료된 표로 내린 REMOVE 판정은 무효다 — 만료 상태면 Tier A 항목도
> ablation(§3-b)을 거친다.

이 파일은 [SKILL.md](../SKILL.md) §3-a의 **1차 선별용**이다. 모델 능력을 평가하는
문서가 아니라, "이 하네스 항목이 모델 능력과 중복인가"만 판정한다.

## 사용법

| Tier | 의미 | 하네스 항목이 여기 해당하면 |
|---|---|---|
| **A** | 지시 없이도 안정적으로 함 | **D1 중복 → REMOVE.** baseline만으로 판정 가능 |
| **B** | 모델·설정·맥락에 따라 갈림 | **ablation 필수.** baseline만으로 REMOVE 금지 |
| **C** | 구조적으로 불가 | **KEEP.** 하네스가 존재해야 하는 영역 |

**표에 없는 능력은 Tier B다.** "당연히 잘하겠지"로 A에 넣지 않는다.

---

## Tier A — 지시 없이도 함 (D1 중복 후보)

프론티어 세대(2025–2026)에서 안정적으로 관측되는 기본기. 이걸 지침으로 적어
두는 것은 상시 토큰을 쓰면서 행동을 바꾸지 않는다.

| 능력 | 이런 규칙이 있으면 D1 중복 |
|---|---|
| 다단계 작업의 분해·계획 수립 | "작업 전에 계획을 세워라", "단계로 나눠 진행해라" |
| 수정 후 자체 검토·명백한 오류 자가 수정 | "코드를 다시 확인해라", "실수가 없는지 검토해라" |
| 주변 코드에서 컨벤션 추론·일치 | "기존 스타일에 맞춰라", "import 순서를 지켜라" |
| 존재하는 테스트·린트 실행 및 실패 해석 | "테스트를 돌려 확인해라", "린트를 통과시켜라" |
| 에러 메시지에서 원인 역추적 | "에러가 나면 원인을 찾아라" |
| 수정 전 관련 파일 읽기 | "파일을 먼저 읽고 수정해라" |
| 상황에 맞는 도구 선택·독립 호출의 병렬화 | "적절한 도구를 써라", "가능하면 병렬로 호출해라" |
| 광범위 탐색 시 검색 도구 사용 | "찾을 때는 grep을 써라" |
| 주류 언어·프레임워크의 관용구 | "파이썬답게 써라", "타입 힌트를 붙여라"(기본 관례 수준) |
| 관례적 커밋 메시지 형식 | "커밋 메시지는 명령형으로" |
| 요청 범위 밖 파일의 임의 생성 자제 | "시키지 않은 파일을 만들지 마라" |
| 자명한 코드에 주석 남발 자제 | "불필요한 주석을 달지 마라" |

**주의** — 이 항목들의 *프로젝트 고유 변형*은 Tier A가 아니다. "테스트를 돌려라"는
Tier A지만 "테스트는 `make check`로만 돌려라"는 환경 사실이므로 **Tier C**다.

## Tier B — 모델·설정·맥락 의존 (ablation 필수)

같은 세대 안에서도 모델·티어·프롬프트·컨텍스트 길이에 따라 갈리는 영역.
baseline만으로 REMOVE 하지 말 것.

| 영역 | 왜 갈리는가 |
|---|---|
| 긴 세션에서 초반 지시의 유지 | 컨텍스트 압축·요약 시점에 유실될 수 있음 |
| 대규모 리팩터에서 전 호출부 갱신 완주 | 범위가 커질수록 누락률이 모델·티어별로 다름 |
| 테스트 통과를 위한 우회(스킵·과잉 목킹) 회피 | 프롬프트·강도 설정에 민감 |
| 커밋·푸시 타이밍 판단 | 사용자 기대가 제각각이라 "옳은 기본값"이 없음 |
| 완료 판정의 엄격함 (어디까지 하면 끝인가) | 모델·설정별 성향 차 |
| 응답 길이·설명 상세도·톤 | 설정과 프롬프트에 크게 좌우됨 |
| 최신 API·라이브러리 버전 사용 | 지식 컷오프에 의존 |
| 비표준·역직관적 프로젝트 컨벤션 준수 | 문서화되어 있으면 함, 없으면 추론 실패 |
| 여러 후보 중 아키텍처 판단 | 정답이 맥락 의존 |

## Tier C — 구조적으로 못 함 (KEEP, 하네스가 필요한 영역)

모델이 좋아져도 사라지지 않는다. 여기 해당하는 항목은 **중복이 아니다.**

| 영역 | 왜 구조적인가 |
|---|---|
| 세션 간 기억 | 상시 로드 지침·메모리 없이는 이전 세션을 모름 |
| 결정론적 보장 ("절대 X 안 함") | 프롬프트는 확률적. permission·훅만이 보장한다 |
| 실행 *전* 차단 | 도구 호출 전에 막는 것은 훅·permission의 영역 |
| 환경 상태 사실 | 자격증명, 내부 엔드포인트, 스테이징 URL, 배포 절차 |
| 조직·팀 규약 | 코드에도 문서에도 없는 합의 |
| 사용자 개인 선호 | 추론 불가 (§선호는 관측되어야 항목이 된다) |
| 지식 컷오프 이후 사실 | 새 API·정책·버전 |
| 프로젝트 고유 검증 명령 | "무엇으로 확인하는가"는 환경 사실 |

## 모델별 주석 (2026-08 기준)

근거를 댈 수 있는 것만 적는다. 불확실한 항목은 적지 않고 Tier B로 남긴다.

- **Claude 5 계열 (Fable 5 / Opus 5 / Sonnet 5)** — Tier A 전반이 안정적.
  이 세대를 기준으로 걷어낸 규칙은 같은 세대 안에서 재사용 가능하다.
- **소형·고속 티어 (Haiku 4.5 등)** — Tier A 중 **긴 다단계 작업의 계획 유지**와
  **대규모 변경 완주**는 Tier B로 내려가는 것으로 취급한다. 상위 모델 기준으로
  걷어낸 규칙이 여기서는 필요할 수 있다 → **다운그레이드 시 전수 재검토**
  (SKILL.md 원칙 4).
- **GPT-5 계열 (Codex CLI)** — Tier A 구성은 유사하나 **강제층의 형태가 다르다**:
  Claude Code의 훅 대신 approval policy·sandbox mode가 그 역할을 한다. 런타임
  중복(D2) 판정 기준이 달라지므로 [codex/SKILL.md](../codex/SKILL.md)를 볼 것.

## 갱신 절차

1. 리뷰 중 표와 어긋나는 실측(ablation 결과)이 나오면 **그 자리에서 기록**한다.
2. 어긋난 항목은 Tier를 옮기고, 버전 스탬프와 근거(어느 모델·언제·무슨 태스크)를
   같이 적는다.
3. 모델 세대가 바뀌면 Tier A 전체를 재검증 대상으로 표시하고, 재검증 전까지는
   Tier A 항목도 ablation을 거친다.
4. **표에 일반론을 쓰지 않는다** — "LLM은 ~를 못한다" 류는 근거가 아니다.
   관측된 태스크와 모델 버전이 함께 적히지 않은 행은 삭제한다.
